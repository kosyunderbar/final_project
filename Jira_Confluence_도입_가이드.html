세 도구의 역할과 연결

Jira 이슈 번호를 브랜치와 커밋 이름에 넣으면 코드가 이슈에 자동으로 연결되고, 규격과 시험 기록은 Confluence 페이지를 이슈에서 링크한다.

이 문서의 규칙과 구성은 모두 제안이다. 시니어 DevOps 엔지니어와 스마트팩토리 엔지니어 역할의 에이전트 의견을 합쳐 썼고, 예시는 HANDOFF.md (2026-11-23 기준)에서 가져왔다.

Jira와 Confluence가 무엇인가

Jira는 할 일을 적는 곳이고 Confluence는 알아야 할 것을 적는 곳이다. 둘 다 Atlassian이라는 회사의 웹 서비스이고, 한 계정으로 같이 쓰며 서로 링크가 걸린다.

Jira를 조금 더 자세히

Jira는 팀의 일을 카드 한 장씩으로 쪼개서, 각 카드가 지금 어느 단계에 있는지 보여 주는 도구다. 처음에는 버그를 추적하려고 만들어졌고, 지금은 소프트웨어 팀이 작업을 관리하는 데 가장 널리 쓰는 도구 가운데 하나다.

메신저나 메모장의 할 일 목록과 다른 점은 세 가지다.

  • 일마다 번호가 붙는다. GT-12 처럼 번호로 부르므로 대화, 커밋, 문서 어디서든 같은 일을 가리킬 수 있다.
  • 일마다 상태가 있다. 할 일인지, 하는 중인지, 끝났는지가 카드의 위치로 보인다. 물어보지 않아도 서로의 진행 상황을 안다.
  • 기록이 남는다. 누가 언제 상태를 바꾸고 무슨 댓글을 달았는지 이슈에 자동으로 쌓인다.

Jira에서 보게 되는 화면은 네 가지다.

보드진행 중인 스프린트의 이슈가 상태별 칸에 카드로 놓인 모습매일. 카드를 옆 칸으로 끌어 상태를 바꾼다

이슈 하나는 이런 순서로 산다.

  1. 누군가 만들어 백로그에 들어간다.
  2. 월요일 계획에서 이번 주 스프린트로 옮겨지고 담당자가 정해진다.
  3. 담당자가 시작하며 '진행 중'으로 옮긴다.
  4. 코드를 올리거나 실물 확인을 기다리며 '검토'로 옮긴다.
  5. 완료 기준을 채우면 '완료'로 옮긴다. 스프린트가 끝나면 보드에서 사라지고 기록으로 남는다. 지난 이슈는 이슈 목록 화면에서 다시 볼 수 있다.

Confluence를 조금 더 자세히

Confluence는 팀이 함께 쓰고 고치는 웹 문서 모음, 즉 위키다. 파일을 주고받지 않고 페이지 주소 하나를 같이 본다. 그래서 "최신 버전이 어느 파일이냐"는 문제가 생기지 않는다.

워드 파일이나 메신저와 다른 점은 네 가지다.

  • 페이지가 나무 모양으로 정리된다. 페이지 아래에 하위 페이지를 두므로, 왼쪽 목록만 봐도 무엇이 어디 있는지 안다.
  • 고칠 때마다 버전이 남는다. 누가 언제 무엇을 바꿨는지 보고, 이전 버전과 비교하거나 되돌릴 수 있다.
  • 문서 위에서 논의한다. 문장을 골라 댓글을 달고, 논의가 끝나면 해결로 표시한다.
  • Jira와 이어진다. 페이지에 Jira 이슈 주소를 붙이면 제목과 현재 상태가 보이는 카드가 된다.

페이지 하나는 제목과 본문으로 이루어지고, 본문에는 글 말고도 여러 요소를 넣을 수 있다.

페이지는 고치는 동안 초안으로 저장되고, 게시를 눌러야 다른 사람에게 보인다. 처음 쓰는 사람이 가장 자주 놓치는 부분이다. Confluence에는 게시 버튼 없이 바로 저장되는 '라이브 문서'도 있다. 버전과 변경 한 줄을 남겨야 하는 규격·결정 문서는 일반 '페이지'로 만든다.

기본 사용법

Jira는 여덟 가지, Confluence는 일곱 가지 동작만 알면 이 프로젝트에 필요한 일을 다 할 수 있다. 버튼 이름은 알고 있는 내용으로 적었고 화면에서 확인하지는 않았다. 표기가 조금 다르면 같은 뜻의 버튼을 찾는다.

Jira 사용법

1. 이슈 만들기

  • 화면 위의 '만들기' 버튼을 누르거나 키보드의 c 를 누른다.
  • 유형을 고르고 요약(제목)을 적는다. 이 두 가지만 있어도 만들어진다. 에픽도 여기서 유형을 '에픽'으로 골라 만든다.
  • 설명에는 완료 조건을 체크리스트로 적는다. 예: [ ] 20번 연속 판독, [ ] 결과를 시험 기록에 적음.
  • 담당자, 상위 항목(에픽), 라벨을 고른다. 나중에 이슈 화면에서 바꿔도 된다. '기한' 칸이 안 보이면 프로젝트 설정의 이슈 유형에서 추가한다.
  • 백로그 아래의 '+ 만들기'를 눌러 제목만 적고 Enter를 눌러도 된다. 여러 개를 빨리 적을 때 좋다.

2. 백로그 정리하기

  • 이슈를 위아래로 끌어 순서를 바꾼다. 위에 있는 것이 먼저 할 일이다.
  • 에픽으로 걸러 보면 한 덩어리의 일만 보인다.

3. 스프린트 만들고 시작하기

  1. 백로그 화면에서 '스프린트 만들기'를 누른다. 빈 스프린트 칸이 생긴다.
  2. 이번 주에 할 이슈를 그 칸으로 끌어 넣는다.
  3. '스프린트 시작'을 누르고 기간(1주)과 목표 한 줄을 적는다. 예: 더미 메시지 1건을 공정 ESP32에서 Spring까지 흘린다.
  4. 시작한 뒤에야 보드에 카드가 나타난다.

4. 보드에서 일하기

  • 일을 시작하면 카드를 '진행 중' 칸으로 끈다. 끝나면 '검토', '완료'로 끈다.
  • 위쪽의 사람 아이콘을 누르면 그 사람의 카드만 보인다.
  • 막힌 카드는 카드 메뉴에서 플래그를 단다. 카드가 눈에 띄는 색으로 바뀐다.

5. 이슈 화면에서 하는 일

  • 댓글. 진행 상황과 결과를 적는다. @이름으로 멘션하면 상대에게 알림이 간다.
  • 이슈 연결. '이슈 연결'에서 관계를 blocks (한국어 화면에서는 '차단함')로 고르고 상대 이슈 번호를 넣는다.
  • 첨부. 로그 파일이나 사진을 끌어다 놓는다.
  • 브랜치 만들기. GitHub를 연동한 뒤에는 개발 칸에서 이슈 키가 들어간 브랜치를 바로 만들 수 있다. 이름 앞의 feature/나 fix/는 직접 붙인다.
  • 기록. 아래쪽 탭에서 이 이슈가 언제 어떻게 바뀌었는지 본다.

6. 스프린트 끝내기

  • 보드나 백로그 화면에서 '스프린트 완료'를 누른다.
  • 끝내지 못한 이슈를 다음 스프린트로 넘길지 백로그로 돌릴지 묻는다. 고르면 끝난다.

7. 이슈 찾기

  • 위쪽 검색창에 번호나 단어를 넣는다. 키보드의 / 를 누르면 검색창으로 간다.
  • 왼쪽 메뉴의 이슈 목록 화면에서는 담당자, 상태, 라벨로 걸러 본다.
  • 목록 화면의 'JQL' 버튼을 누르면 JQL이라는 검색 문장을 직접 쓸 수 있다. 자주 쓸 두 가지만 알아 둔다.
assignee = currentUser() AND statusCategory != Done
labels = icd ORDER BY updated DESC

첫 줄은 내가 맡은 일 중 안 끝난 것, 둘째 줄은 규격에 영향을 주는 이슈를 최근에 바뀐 순서로 보여 준다.

8. 타임라인 보기

  • 에픽마다 시작일과 끝나는 날을 넣으면 달력 위에 막대로 보인다. 달력 위에서 에픽 줄을 눌러 끌면 기간이 잡히고, 막대를 끌어 날짜를 바꾼다.
  • 12-18 촬영 마감까지 에픽 9개가 어떻게 놓이는지 한 화면에서 볼 수 있다.

자주 쓰는 단축키는 c (만들기), / (검색), i (나에게 배정), m (댓글)이다. ? 를 누르면 전체 목록이 나온다. 단축키는 영문 입력 상태에서 동작하고, i와 m은 이슈를 열었을 때 쓴다.

Confluence 사용법

1. 페이지 만들기

  • 왼쪽 페이지 목록에서 상위 페이지 옆의 + 를 누르면 그 아래에 하위 페이지가 생긴다.
  • 위쪽의 '만들기'로도 만들 수 있다. 이때는 어느 페이지 아래에 둘지 확인한다.
  • 제목을 적는다. 템플릿 목록이 옆에 뜨면 회의록 같은 틀을 고를 수 있다.

2. 본문 쓰기

  • 그냥 입력하면 된다. 제목 크기와 굵게 같은 서식은 위쪽 도구 모음에 있다.
  • / 를 입력하면 넣을 수 있는 요소의 목록이 뜬다. 표, 작업 목록, 정보 패널, 상태, 날짜, 코드 블록, 목차를 이렇게 넣는다. 이것 하나만 외워도 대부분의 페이지를 만든다.
  • @이름으로 사람을 멘션한다.
  • 사진이나 파일은 본문에 끌어다 놓는다.

3. 게시하기

  • 쓰는 동안에는 초안으로 자동 저장된다. 이 상태는 다른 사람에게 보이지 않는다.
  • 오른쪽 위의 '게시'를 눌러야 보인다. 이미 게시한 페이지는 오른쪽 위의 '편집'(연필 모양, 단축키 e)을 눌러 고친 뒤 '업데이트'를 누른다.
  • 버튼을 누르면 바로 반영된다. 무엇을 바꿨는지 한 줄을 남기려면 버튼 옆 ⋯ 메뉴의 '버전 댓글과 함께 게시'를 쓴다. 규격 페이지는 항상 이렇게 한다. 예: 태그 읽음에 신고 번호 필드 추가 (GT-31).

4. 댓글로 논의하기

  • 본문의 글자를 끌어 고르면 댓글 버튼이 뜬다. 그 문장에 붙는 댓글이 된다.
  • 페이지 맨 아래에는 페이지 전체에 대한 댓글을 단다.
  • 문장에 단 댓글은 논의가 끝나면 '해결'을 눌러 닫는다. 맨 아래 댓글에는 해결 버튼이 없으니, 규격 논의는 문장에 다는 댓글로 한다.

5. Jira와 잇기

  • Jira 이슈의 주소를 본문에 붙여 넣으면 제목과 상태가 보이는 카드로 바뀐다. 이슈가 완료되면 카드의 상태도 바뀐다.
  • 반대로 Jira 이슈에는 Confluence 페이지 주소를 링크로 단다.
  • 회의록에서 나온 할 일은 페이지에 적는 데서 그치지 않고 Jira 이슈로 만든 뒤 그 주소를 회의록에 붙인다.

6. 이전 버전 보기

  • 페이지 오른쪽 위의 ⋯ 메뉴에서 '페이지 기록'을 연다.
  • 두 버전을 골라 비교하면 바뀐 부분에 색이 칠해진다. 이전 버전으로 되돌릴 수도 있다.
  • "규격이 언제 바뀌었지?"라는 질문은 여기서 답한다.

7. 정리하고 따라가기

  • 왼쪽 목록에서 페이지를 끌어 다른 페이지 아래로 옮긴다.
  • 페이지 오른쪽 위나 ⋯ 메뉴의 '지켜보기'를 켜면 그 페이지가 바뀔 때 알림을 받는다. 두 사람 모두 인터페이스 규격 페이지를 지켜본다.
  • 자주 쓰는 틀은 스페이스 설정의 템플릿 메뉴에서 미리 만들어 둔다. 시험 기록이 그런 페이지다.

왜 쓰는가

합치는 날 생기는 문제의 대부분은 코드 버그가 아니라 "서로 다르게 알고 있었다"이고, 두 도구는 그것을 막는다. 스마트팩토리 프로젝트는 펌웨어, 통신, 서버, 화면, 기구물을 서로 다른 사람이 따로 만들어 마지막에 합치기 때문이다.

남겨야 하는 것없으면 생기는 일두는 곳
인터페이스 규격 (현업에서는 ICD, Interface Control Document라고 부른다)보드는 필드 4개를 보내는데 서버는 3개를 기다린다Confluence
누가 무엇을 언제까지, 누구의 일이 누구를 막는가실측이 늦어 트윈 맵까지 밀린 것을 마지막 주에 안다Jira
구매, 3D 출력, 실측처럼 코드가 남지 않는 일어디에도 기록이 없다Jira
시험 기록"된다"가 "어떤 조건에서 20번 중 몇 번"인지 모른다Confluence
결정 기록같은 논의를 반복하고, 제안을 확정으로 착각한다Confluence

이 프로젝트에서 얻는 것은 세 가지다.

  • 두 사람의 경계가 문서로 남는다. 나는 하드웨어 쪽, 팀원은 디지털 트윈 쪽을 맡고 그 밖의 일은 생기는 대로 맡는다. 둘이 만나는 곳은 MQTT 메시지, HTTP 규격, DB 구조이고, 양쪽은 상대의 코드가 아니라 규격 페이지를 보고 만든다.
  • 발표 자료의 근거가 쌓인다. 발표가 PT와 시연 영상이라, 시험 기록과 결정 기록이 그대로 발표 근거가 된다.
  • 현업 도구를 실제 프로젝트로 익힌다. 수업 명세서에는 Jira·Confluence 요구가 없다. 필수가 아니므로 가볍게 쓰고, 맞지 않는 부분은 줄여도 된다.

시나리오 1: 내가 MQTT 메시지 형식을 바꿔야 할 때

  1. 코드를 고치기 전에 Jira 이슈를 만든다. 태그 읽음 메시지에 신고 번호 필드를 넣어 재전송을 구분한다, 라벨 icd.
  2. Confluence의 MQTT 규격 페이지에 '변경 제안' 칸을 만들어 바뀌는 필드, 이유, 영향받는 쪽을 적는다. 현재 판의 표는 건드리지 않는다.
  3. 팀원에게 확인을 요청한다. 팀원 쪽에 고칠 것이 있으면 팀원이 이슈를 만들고 blocks로 잇는다.
  4. 논의는 페이지 댓글에서 하고, Jira에는 결론 한 줄만 남긴다.
  5. 합의되면 내가 규격 표를 고치고 판을 v0.2로 올린 뒤 변경 이력에 한 줄을 더한다.
  6. 양쪽이 구현한다. 커밋 메시지에 이슈 번호를 적는다.
  7. 둘이 함께 메시지 한 건을 실제로 주고받아 시험 기록에 남기고 두 이슈를 닫는다.

시나리오 2: 한 주(11-23~11-29)를 계획하고 닫기

  1. 주 시작 15분. 보드를 같이 보며 지난주에서 넘어온 일(키트 검수, RC522·ESP32 구매, 태그 팟 끼움 확인)이 어디까지 됐는지 확인하고, 11-24 책상 위 시험에 필요한 것부터 이번 주로 옮긴다.
  2. 날짜가 걸린 것을 먼저 올린다. 이번 주는 11-24 책상 위 ESP32 + RC522 + 버튼 + LED + 서보와 connect 막힘 측정·두 태스크 뼈대, 11-26 작업 순서·다시 보내기와 Pi5 끄기 시험, 11-28 P2 한 곳 연동(기록·HMI)이다. 다음 주 12-01 RTOS 판정과 12-04 공정 1안 완성(공정마다 20번 연속)도 이번 주 결과에 달려 있다.
  3. 각자 이번 주에 끝낼 이슈를 3~5개만 고른다. 나는 connect 막힘 측정, 두 태스크 뼈대, 색 구역 위치 실측, 팀원은 Spring 실행 위치·DB 결정과 수신 엔드포인트.
  4. 서로 막는 것을 말로 확인한다. "색 구역 위치 실측이 수요일까지 안 나오면 트윈 맵 좌표는 다음 주." "P2 연동이 11-28을 넘기면 12-01 RTOS 판정 근거가 모자란다."
  5. 주중. 시작하면 '진행 중'으로 옮긴다. 막히면 이슈에 이유를 한 줄 적는다. 측정값은 시험 기록 페이지에 적는다.
  6. 주 끝 15분. 완료 조건이 채워진 것만 닫는다. 못 끝낸 것은 이유를 적고 넘기거나 범위를 줄인다.

세팅법

한 사람이 1~7단계를 반나절 안에 끝내고, 다른 사람은 초대 메일만 수락하면 된다. Atlassian 화면은 자주 바뀌므로 메뉴 위치가 다르면 이름으로 찾는다. 한도와 메뉴 이름은 웹에서 다시 확인하지 않고 알고 있는 내용으로 적었다. '확인 필요'라고 적은 곳은 가입 화면에서 직접 본다.

1단계: Atlassian Cloud 가입과 사이트 생성

  • atlassian.com에서 Jira 무료 시작을 고르고 이메일(구글 계정 가능)로 가입한다.
  • 사이트 이름을 정하면 주소가 https://<이름>.atlassian.net 이 된다. 나중에 바꾸기 번거로우니 짧게 정한다.
  • 무료 플랜은 Jira와 Confluence 각각 사용자 10명, 저장 용량 2GB로 알고 있다. (확인 필요)
  • 가입 중에 나오는 설문은 아무거나 골라도 된다.

2단계: Jira 프로젝트 만들기

고를 것선택이유
템플릿스크럼마감이 고정된 5주 프로젝트라, 매주 "이번 주에 끝낼 것"을 정하는 편이 일정 관리에 맞다. 칸반은 기간 없이 카드만 흘려보내는 방식이다
유형팀 관리형(team-managed)설정이 프로젝트 안에서 끝난다. 회사 관리형은 여러 프로젝트가 설정을 공유할 때 쓰는 유형이라 배울 것만 늘어난다
프로젝트 키영문 대문자 2~3자. 이 문서의 예시는 GT이슈 번호(GT-1), 브랜치, 커밋에 계속 쓰이므로 처음에 확정한다
  • 프로젝트 유형은 만든 뒤에 바꿀 수 없고, 새로 만들어 이슈를 옮겨야 하는 것으로 알고 있다. (확인 필요)
  • 최근 Jira 화면은 '이슈'를 '업무 항목(work item)'으로, '프로젝트'를 '스페이스(space)'로 표기할 수 있다. 같은 것이다. 이 문서는 Confluence 스페이스와 헷갈리지 않게 Jira 쪽을 '프로젝트'라고 부른다.
  • 보드의 칸을 할 일, 진행 중, 검토, 완료 네 개로 맞춘다. 기본 세 칸에 검토 하나를 더하고 완료 앞으로 끌어 옮긴다. 이 칸의 상태 분류는 '진행 중'으로 둔다. '완료'로 두면 검토 중인 일이 끝난 것으로 집계된다. 스프린트를 시작하기 전에는 보드가 비어 보인다.
  • 연동 확인에 쓸 이슈 하나(GT-1, 예: 새 레포 초기 구성)만 먼저 만든다. 에픽 9개와 첫 주 이슈는 6단계에서 연동을 확인한 뒤에 만든다.

3단계: Confluence 스페이스 만들기

  • 같은 사이트에 Confluence를 추가한다. 화면 왼쪽 위의 앱 전환 아이콘(격자 모양)이나 admin.atlassian.com의 제품 추가에서 한다. (위치 확인 필요)
  • 스페이스는 하나만 만든다. 빈 스페이스로 시작해 앞 절의 페이지 트리에서 최상위 7개만 제목으로 만들어 둔다.
  • 내용은 필요할 때 채운다. 회의록은 Confluence에 들어 있는 회의록 템플릿을 그대로 쓴다.

4단계: 팀원 초대

  • Jira 상단의 사용자 초대나 admin.atlassian.com의 사용자 메뉴에서 이메일로 초대한다. (메뉴 이름 확인 필요)
  • Jira와 Confluence 접근 권한을 둘 다 준다.
  • 팀원에게도 admin.atlassian.com에서 관리자 역할을 준다. 한 명만 관리자면 그 사람이 없을 때 앱 설치나 사용자 관리를 못 한다.

5단계: 새 GitHub 레포 만들기

코드 레포는 하나로 하고, Unreal 프로젝트만 따로 둔다. 한 레포에 두면 펌웨어와 서버를 한 PR(Pull Request, 브랜치를 main에 합쳐 달라는 요청)에서 같이 바꿀 수 있고 규칙과 연동이 한 벌이면 된다.

Unreal은 용량이 큰 에셋 파일 때문에 레포가 무거워지고, GitHub는 100MB가 넘는 파일의 push를 거부한다. Unreal 레포에는 Unreal용 .gitignore와 Git LFS(큰 파일 전용 저장 기능)를 쓴다. 레포는 무료 GitHub Organization을 만들어 그 아래에 두고 팀원을 초대한다. 개인 계정 레포보다 Jira 연동과 권한 문제가 적다. 기존 기획 레포는 참고 자료로 남기고, 그 안의 HMI 시안과 CAD 스크립트는 새 레포로 복사해 온다.

6단계: GitHub와 Jira 연동

  1. Jira 상단의 앱(Apps) 메뉴에서 GitHub for Jira (제작사 Atlassian, 무료)를 찾아 설치한다. 앱 이름이 GitHub for Atlassian으로 바뀌어 보일 수 있다. (확인 필요)
  2. 설정 화면에서 팀의 GitHub Organization을 연결하고 이 프로젝트의 레포만 선택한다. Jira 사이트 관리자와 GitHub Organization 소유자 권한이 모두 필요하다. Unreal 레포도 함께 선택한다.
  3. 확인한다. GT-1 이슈의 키를 넣은 feature/GT-1-repo-init 브랜치를 push한 뒤, 이슈 화면에 브랜치가 보이는지 본다. 반영에 몇 분 걸릴 수 있다.

원리는 단순하다. 브랜치 이름, 커밋 메시지, PR 제목에 이슈 키(GT-12)가 있으면 그 이슈 화면에 자동으로 나타난다.

7단계: 레포에 규칙 장치 두 개 넣기

PR 템플릿은 .github/pull_request_template.md 에 둔다.

## 이슈: GT-
## 무엇을 바꿨나
## 어떻게 확인했나 (실물/모의, 로그·사진)
- [ ] 인터페이스(토픽·메시지·스키마)가 바뀌었으면 규격 페이지를 먼저 고쳤다
- [ ] 비밀 값이 들어 있지 않다

커밋 메시지에 이슈 키가 없으면 막는 훅은 .githooks/commit-msg 에 두고, 각자 클론한 뒤 git config core.hooksPath .githooks 를 한 번 실행한다. 파일에는 실행 권한이 필요하다. Mac에서는 chmod +x .githooks/commit-msg, Windows에서는 git update-index --chmod=+x .githooks/commit-msg를 한 번 실행해 커밋한다.

#!/bin/sh
grep -v '^#' "$1" | grep -qE '(^|[^A-Za-z0-9])GT-[0-9]+|^Merge |^Revert ' || {
  echo "커밋 메시지에 이슈 키(예: GT-12)가 없습니다."; exit 1; }

main 브랜치는 직접 push를 막고 PR을 거치게 한다. 무료 플랜의 비공개 레포에서는 이 보호가 적용되지 않는다. 공개 레포이거나 유료 플랜이어야 한다. 비공개 레포를 쓴다면 "main에 직접 push하지 않는다"는 약속으로 대신한다.

팀 규칙

널리 쓰이는 규칙 가운데 2인 팀과 5주 일정에 맞는 것만 골라 10가지로 정했다. 모두 제안이며, 두 사람이 첫 회의에서 확정한다.

번호규칙이유예시
1이슈 계층은 에픽과 이슈 2단만. 하위 작업은 쓰지 않고 설명란의 체크리스트로 대신한다2인 팀에서 3단 계층은 관리할 것만 늘어난다유형은 스토리(눈에 보이는 동작), 작업(세팅·문서·실측·구매), 버그(되던 것이 안 됨). 헷갈리면 전부 작업
2상태는 할 일 → 진행 중 → 검토 → 완료 네 개상태가 많으면 카드를 옮기는 일 자체를 안 하게 된다검토 는 PR이 열렸거나 실물 확인을 기다리는 상태. 막힌 일은 상태를 만들지 않고 카드 메뉴에서 플래그(깃발)를 단다
3이슈 제목은 무엇을 해서 무엇이 된다끝났는지 제목만 보고 판별할 수 있어야 한다좋음: P2 공정 ESP32가 답이 올 때까지 신고를 다시 보낸다. 나쁨: 펌웨어 수정
4이슈 하나는 하루에서 이틀. 넘으면 쪼갠다. 스토리 포인트는 쓰지 않는다포인트는 여러 스프린트의 기록이 쌓여야 의미가 있는데 5번으로는 쌓이지 않는다AGV 선 따라가기를 카메라 영상 받기, 선 찾기, 조향, 정지 위치 판정으로 쪼갠다
5'진행 중'은 한 사람에 최대 2개. 플래그를 단 대기 이슈는 세지 않는다부품을 기다리는 일이 있어 1개로는 부족하지만, 3개를 넘으면 아무것도 끝나지 않는다배송 대기로 막히면 플래그를 달고 다음 이슈를 시작한다
6완료 기준: ① main에 합쳐짐(코드인 경우) ② 실물이나 정해 둔 모의 방법으로 동작을 확인함 ③ 인터페이스가 바뀌었으면 규격 페이지가 고쳐져 있음 ④ 이슈에 증거(로그, 사진, 시험 기록 링크)가 한 줄 있음"내 보드에서는 됐다"와 "합쳐서 된다"의 차이가 마지막 주에 터지는 것을 막는다댓글: mosquitto_sub로 태그 읽음 수신 확인, 로그 첨부
7브랜치는 GitHub Flow: main 하나에서 짧은 브랜치를 따고 PR로 합친다. 이름은 유형/키-짧은설명develop·release 브랜치를 두는 Git Flow는 배포 버전을 관리하는 팀용이다feature/GT-12-process-fsm, fix/GT-31-mqtt-reconnect. 유형은 feature, fix, docs, chore. 브랜치는 하루에서 이틀 안에 합친다
8커밋 메시지는 Conventional Commits 형식에 이슈 키를 넣는다: 유형(범위): 키 내용키가 있어야 Jira에 연결되고, 범위가 있어야 한 레포 안에서 어느 부분인지 보인다feat(fw-esp32): GT-12 설비 태스크 상태 기계 추가. 유형은 feat, fix, docs, refactor, test, chore 6개. 범위는 레포 폴더 기준으로 fw-esp32, agv, tag, pi, server, web
9PR 하나는 이슈 하나. 자기 영역만 바꾸는 PR은 올려서 알린 뒤 바로 합쳐도 된다. 단, 인터페이스(MQTT 토픽·메시지, Pi5↔Spring HTTP, DB 구조)를 바꾸는 PR은 상대가 승인한 뒤에만 합친다모든 PR을 기다리면 2인 팀은 멈춘다. 인터페이스는 양쪽 코드가 함께 깨지는 유일한 지점이다PR 제목 feat(fw-esp32): GT-12 설비 태스크 상태 기계 추가. 스쿼시 병합(PR의 커밋을 하나로 합쳐 넣기)을 쓴다. PR 제목이 main의 커밋 메시지가 되므로 커밋과 같은 형식으로 쓴다
10스프린트는 1주, 월요일 시작. 회의는 세 가지: 월요일 계획, 매일 10분, 금요일 마무리. Jira의 스프린트 완료 처리는 다음 월요일 계획 직전에 하고, S5만 12-24 목요일에 한다2주 스프린트로는 5주 동안 계획을 고칠 기회가 2번뿐이다매일 10분은 보드를 보며 어제 한 것, 오늘 할 것, 막힌 것만 말한다

규격의 원본은 한 곳

인터페이스 규격의 원본은 Confluence의 규격 페이지로 한다. 레포에는 복사본을 두지 않고, README에 링크와 현재 판 번호만 적는다. 표를 고치고 댓글로 논의하기 쉽고, 웹에서 바로 볼 수 있기 때문이다.

다른 선택도 있다. 레포의 docs/interface/ 에 두면 규격과 코드를 한 PR에서 같이 고칠 수 있어 어긋날 일이 줄어든다. 어느 쪽이든 두 곳에 같은 내용을 쓰지 않는 것이 규칙이다.

하지 않기로 하는 것

이 규모에서는 시간만 드는 것들이다.

  • 회사 관리형 프로젝트, 커스텀 워크플로, 권한 설계
  • 상태 5개 이상, 보드 여러 개, Jira 프로젝트 여러 개
  • 스토리 포인트 추정 회의, 번다운 차트 분석, 작업 시간 기록
  • Jira 자동화 규칙, 커밋 메시지로 이슈 상태를 바꾸는 스마트 커밋
  • Git Flow, 버전 태그와 릴리스 노트
  • 펌웨어 자동 빌드(CI), commitlint, 코드 커버리지
  • 유료 플랜과 추가 앱. GitHub for Jira 하나면 된다
  • 도구 세팅에 하루 이상 쓰기. 세팅은 반나절에 끝내고, 불편한 점은 금요일에 한 가지씩만 고친다

이 프로젝트에 맞춘 팁

  • 측정값은 댓글이 아니라 시험 기록 페이지에 적는다. 이슈에는 페이지 링크와 "20번 중 n번" 한 줄만 남긴다.
  • 확정, 제안, 실물 검증 전을 그대로 적는다. 지금은 거의 모든 숫자가 추정이다. '추정' 표시가 빠지면 2주 뒤에 실측값으로 오해한다.
  • 하나뿐인 자원은 시간표로 관리한다. JETANK는 1대인데 주행 시험과 촬영이 나눠 쓴다. 프린터실과 교육장 맵도 같다. Confluence 홈에 사용 시간표를 두고 이슈 마감일을 거기에 맞춘다.
  • 위험이 큰 일은 먼저, 작게 한다. 공정 ESP32의 RTOS판이 12-01까지 안정되지 않으면 loop판으로 돌아간다. 이렇게 되돌아갈 길을 미리 정해 두고, 판정에 필요한 이슈는 우선순위를 가장 높게 둔다.
  • 촬영 장면을 이슈와 연결한다. 장면 목록 페이지에 장면마다 "이 장면을 찍으려면 끝나 있어야 하는 이슈"를 적는다. 촬영 마감에서 거꾸로 세면 무엇을 버려야 하는지 보인다. 시연·시험 영상은 용량이 크므로 Google Drive 같은 곳에 올리고 Confluence에는 링크만 둔다.
  • 이슈 없이 급히 고칠 일에 대비한다. 잡일이라는 상시 이슈를 하나 만들어 두면 커밋 규칙이 깨지지 않는다. 이 이슈는 스프린트에 넣지 않고 백로그에만 둔다.
