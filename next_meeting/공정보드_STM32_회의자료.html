공정 보드 구성 — STM32를 왜, 어떻게 쓰나

2026-11-21 · 에이전트 회의 3인 2라운드(ESP32 단독파 · 제어기 분리파 · 심사·팀장 관점) + Claude 의견 · 모두 제안, 팀 결정 전 · 공정별 센서는 아직 정하지 않음 · 실물 시험은 아직 하나도 안 함

나온 질문

“ESP32 하나면 충분한데, 왜 STM32·Renesas를 굳이 붙이나?”
기술적으로는 맞는 말이다. 이번 공정(서보·등·부저·RFID·버튼) 정도는 ESP32 하나로 돌릴 수 있다. 성능 때문에 붙인다는 설명은 통하지 않는다.
그냥 붙이면 ‘굳이’가 맞다.
MCU에 판단을 맡기면 붙일 가치가 있다.
세 에이전트 모두 이 결론에 동의했다. 처음 ‘굳이’를 주장한 에이전트도 2라운드에서 인정했다. ESP32만 쓰자(C안)는 아무도 최종안으로 고르지 않았다.

MCU가 직접 맡을 일 4가지 — 없으면 ‘굳이’

역할내용
비상정지버튼이 눌리면 MCU가 즉시 멈추고 그 상태를 유지. 해제는 현장 버튼으로만(Pi5 명령으로는 못 푼다)
작업 순서Pi5의 허가를 한 번 받으면 단계와 시간을 MCU가 끝까지 혼자 진행
거부권허가가 와도 태그 없음·비상정지·센서 이상이면 움직이지 않고 이유를 알림
이상 판단센서 기준값 판단을 MCU가 하고 결과만 보고 (센서 종류는 미정)

역할 나누기 — 입, 손과 브레이크, 공장 두뇌

발표 때 받을 질문: “왜 MCU를 따로 붙였나요?”

점수가 되는 답“ESP32는 통신만 하고, 순서·비상정지·이상 판단·끊김 대응은 MCU가 맡습니다.” + 위 ①~④ 장면 영상
깎이는 답“현업에서 많이 써서요”, “써 보고 싶어서요”, “Pi5가 다시 보내 줍니다” → 붙여 놓은 장식으로 보인다
팀원 설득용 한 문장(심사·팀장 관점 에이전트): “ESP32는 말하는 입, STM32는 손과 브레이크다. 입을 막아도 공정이 안전하게 멈추는 장면을 찍으면 ‘왜 붙였냐’는 질문이 오히려 점수가 된다.”

왜 Renesas가 아니라 STM32인가

Renesas가 나쁜 보드라서가 아니다. 성능은 Renesas가 더 높다. 이번 프로젝트의 일정·예제·도구 수 때문이다. · 13-3 결정(“STM32 2 + Renesas 2를 반드시 사용”)을 바꾸는 일이라 팀 결정이 필요하다.

STM32로 맞추자는 이유

  1. 성능 차이가 필요 없다. 서보·등·부저·RFID는 72MHz로 충분하다. Renesas의 장점이 이번 공정에서는 쓰이지 않는다.
  2. 시간이 없다. 12-04 공정 1안까지 13일. RFID 코드를 받아 쓰느냐 고쳐 쓰느냐가 그대로 일정 차이다.
  3. 도구가 하나 준다. CubeIDE · e² studio · Arduino(ESP32) 세 개 → CubeIDE · Arduino 두 개.
  4. 같은 코드를 네 곳에 복사한다. P1·P2 코드를 P3·P4에 거의 그대로 쓴다. 고장 찾기와 담당 교대도 쉽다.
  5. 발표에서 약점이 된다. 가장 단순한 P3·P4에 예제가 가장 적은 보드를 쓴 셈이라 “왜?”라는 질문에 답하기 어렵다(심사·팀장 관점).

Renesas는 버리지 않고 시험 기회를 준다

  • 11-24~26, 이틀로 끊는다. 1일차: ESP32와 UART 주고받기, 검사값(XOR) 확인. 2일차: RC522 연결(SPI).
  • 통과하면 P4 한 곳에 선택적으로 쓴다(“두 회사 보드로 옮겨 봤다”는 이야기가 생긴다).
  • 실패하면 더 붙잡지 않는다. 다시 회의하지 않고 STM32로 간다.
  • 코드는 처음부터 부품 동작 / 보드 의존 두 층으로 나눠 짠다. 그러면 보드를 바꿔도 손볼 곳이 함수 몇 개다.

두 가지 안 — B: STM32 4대로 통일 / B′: 판단거리 있는 공정만 STM32

두 안 모두 ESP32는 공정마다 1대씩 4대(+ 스마트태그 1대, 총 5대)를 쓴다. 검사는 두 안 모두 Pi5 #2 + 카메라. · 지지: B = 제어기 분리파 · 심사·팀장 관점 · Claude / B′ = ESP32 단독파

두 안 비교

B — STM32 4대 통일B′ — STM32 2 + ESP32 혼자 2
추가 구매NUCLEO 2대없음

발표 설명“모든 공정은 같은 구조: 입(ESP32) + 손과 브레이크(STM32)”“판단할 일이 있는 공정에만 제어기를 둔다” — “왜 거기만?” 질문이 나온다
좋은 점코드 복사, 설명이 단순, 담당 교대 쉬움돈이 안 들고, 단순한 공정은 빨리 끝난다
나쁜 점구매비, STM32 4대 배선·시험코드가 두 갈래, 공정마다 고장 찾는 법이 다르다
공정별 센서는 아직 정하지 않았다. HANDOFF 16절의 센서(P1 진동, P2 초음파, P3·P4 없음 등)는 후보일 뿐이다. B′를 고르면 센서부터 정해야 하고, B는 센서와 따로 정할 수 있다.

Claude 의견: B를 권한다

  • B′는 보드를 덜 쓰지만 공정 코드가 두 종류가 되어 일이 오히려 는다.
  • 센서가 없는 공정도 비상정지·작업 순서·거부권(태그 없으면 안 움직임)은 MCU가 맡을 수 있다.
  • 센서 결정을 기다리지 않고 지금 보드를 정할 수 있다.

참고: 고르지 않은 안

  • A 지금대로(STM32 2 + Renesas 2): 할 이야기는 많지만 Renesas 위험과 도구 3개가 그대로 남는다.
  • C 전부 ESP32: 가장 빠르지만 끊김 장면을 못 찍고, 임베디드 트랙에서 ‘아두이노 수준’으로 보일 위험. ESP32 단독파도 최종안으로 고르지 않았다.

어떻게 진행하나 — 순서, 날짜 기준, 회의에서 정할 것

날짜는 세 에이전트 의견을 합친 제안이다. 팀 일정으로 확정한 것이 아니다.

먼저 만들 것: ESP32 통신 다리 코드

  • ESP32가 UART 한 줄 ↔ MQTT를 옮기는 코드만 먼저 짠다. 4대 모두 같은 코드다.
  • 공정 보드가 없어도 PC 터미널에서 줄을 직접 쳐서 ‘공정 보드인 척’ 하면 Pi5 기록·HMI·AGV 연동을 바로 시작할 수 있다.
  • B든 B′든 버릴 코드가 없다. MCU가 끝내 안 되면 이 코드에 RFID를 붙여 ESP32 혼자 쓰는 공정으로 바꾼다(13-3 ‘ESP32는 통신만’을 바꾸는 일이라 팀 결정 필요).

통신 끊김 장면 — 범위를 작게

작업 중에 공유기 전원을 끄거나 ESP32 리셋 버튼을 누른다 → 서보가 안전 위치로 가서 멈춤 → 상태등 빨강 깜빡 → 다시 연결 → HMI에 밀린 기록이 같은 번호로 한 번만 들어감. 넣는 것은 비상정지, 끊김 시 정지, 작은 재전송 대기열까지만.

안전 배선 (안과 상관없이)

  • 비상정지 버튼은 하드웨어로도 끊는다. 평소 닫힘 접점을 모터 전원선에 직접 넣고, 같은 신호를 MCU 입력에도 연결한다. 진짜 안전장치는 펌웨어가 아니라 전원 차단이다(ESP32 단독파 지적, 모두 동의).
  • 모터 전원은 보드와 따로. 서보와 같은 전원을 쓰면 Wi-Fi 송신 순간 전압이 떨어져 칩이 리셋될 수 있다.

회의에서 정할 것

  1. B / B′ (A·C 포함). B와 B′는 13-3 “Renesas 반드시 사용”을 바꾼다.
  2. Renesas를 T1 결과로 정하는 것에 동의하는지, Renesas를 써 본 팀원이 있는지.
  3. NUCLEO 2대 구매 여부와 시점(지금 / 11-26 뒤).
  4. MCU 4역할 채택. 채택하면 18절이 바뀐다: Pi5의 작업 허가는 ‘해도 된다’는 요청이 되고 최종 판단은 MCU. 상태등은 평소 Pi5를 따르고 이상·끊김 때는 MCU가 먼저.
  5. MCU가 안 될 때 RFID를 ESP32로 옮겨도 되는지(13-3 변경).
  6. 공정별 센서 확정. B′를 고르면 이것부터 정해야 한다.
  7. 담당: STM32 공정 코드, ESP32 통신 코드, Renesas T1.
