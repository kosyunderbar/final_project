이렇게 말하지 않는다. ‘고장 분리’가 아니다 — 칩이 통째로 리셋되면 둘 다 멈춘다(그건 워치독과 전원 차단 배선이 맡는다). ‘RTOS라서만 된다’도 아니다 — 잘 짠 loop로도 가능하다. RTOS는 그걸 구조로 보장하는 방법이다.

뼈대 코드 — 전체 모양은 이 정도 (약 30줄 · 컴파일 확인 전 · 단순화 예시)

QueueHandle_t toComm, toCtrl;          // 메모 꽂이 두 개
struct Msg { char line[160]; };
void ctrlTask(void*) {                  // 설비 담당
  TickType_t t = xTaskGetTickCount();
  for (;;) {
    if (digitalRead(BTN) == LOW) {      // 버튼을 보고
      Msg m; snprintf(m.line, sizeof m.line, "$R{\"k\":\"BTN\"}");
      xQueueSend(toComm, &m, 0);        // 메모를 꽂는다 (기다리지 않음)
    }
    Msg in;
    while (xQueueReceive(toCtrl, &in, 0)) { /* 받은 명령 처리 */ }
    vTaskDelayUntil(&t, pdMS_TO_TICKS(10));   // 0.01초 박자
  }
}
void commTask(void*) {                  // 통신 담당
  for (;;) {
    serviceWifi(); serviceMqtt();       // 지금 modem.ino 그대로 (여기서 막혀도 됨)
    Msg out;
    while (xQueueReceive(toComm, &out, 0)) publishLine(out.line);
    vTaskDelay(pdMS_TO_TICKS(5));
  }
}
void setup() {
  toComm = xQueueCreate(8, sizeof(Msg));
  toCtrl = xQueueCreate(8, sizeof(Msg));
  xTaskCreatePinnedToCore(ctrlTask, "ctrl", 6144, nullptr, 3, nullptr, 1);
  xTaskCreatePinnedToCore(commTask, "comm", 8192, nullptr, 2, nullptr, 0);
}
void loop() { vTaskDelete(nullptr); }

상태 기계 (공정 공통 뼈대)

BOOT → IDLE(대기) → WAIT(태그 읽음, 허가 대기) → WORK(작업, 공정별 동작 표) → DONE(작업 끝 신고, 답 대기) → IDLE
어디서든 → FAULT(비상정지·센서 이상·Pi5가 보낸 이상) → 현장 길게 누름 + 원인 없음 → 처음부터
‘끊김’은 상태가 아니라 덧씌우는 표시: 하던 동작은 끝내고 새 작업만 막는다

지킬 규칙 다섯

  1. 함께 쓰는 변수 0개. 주고받는 것은 모두 큐로.
  2. 한 장치는 한 태스크만. MQTT·Wi-Fi는 통신, SPI·핀은 설비. (PubSubClient는 여러 태스크가 같이 부르면 안 된다)
  3. 설비는 기다리지 않는다. 큐는 기다림 0으로 꺼내고, delay() 대신 vTaskDelayUntil로 10ms 박자.
  4. 큐가 차면 신고는 버리지 않고 설비의 ‘다시 보낼 목록’에 남긴다. 연결 상태 줄은 오래된 것을 버린다.
  5. 로그는 한 줄씩 [C]/[N] 표시. 두 태스크가 Serial에 동시에 쓰면 섞인다.

워치독 · 부팅

  • 두 태스크를 태스크 워치독에 등록. 전체 제한 시간 약 8초로 시작(접속 대기보다 길게, 측정 후 확정). 코어 3.x는 IDF 5 함수 이름(확인 필요).
  • 워치독이 터지면 재시작 → 안전 자세(서보 원위치, LED 꺼짐) → BOOT 신고 → 작업 중이었다면 Pi5가 ‘작업 중 재시작(F04)’으로 적고 현장 버튼으로 푼다.
