전체 그림

공정 보드 한 대가 하는 일은 두 종류입니다. 리더기를 읽고 버튼을 보고 설비를 움직이는 일은 기다리면 안 됩니다. Wi-Fi와 MQTT는 상대가 답하지 않으면 몇 초씩 기다릴 수밖에 없습니다. 이 둘을 태스크 두 개로 나누고, 사이를 큐 두 개로만 잇습니다.

지키는 규칙 다섯 가지

  1. 같이 쓰는 변수는 0개. 두 태스크가 주고받는 것은 모두 큐로 보냅니다.
  2. 한 장치는 한 태스크만 만집니다. Wi-Fi, MQTT, Serial은 통신 태스크만. 리더기(SPI)와 공정 핀은 설비 태스크만.
  3. 설비 태스크는 기다리지 않습니다. 큐는 기다림 0으로 꺼내고 delay()를 쓰지 않습니다.
  4. 큐가 차도 신고는 버리지 않습니다. "다시 보낼 목록"에 남겨 같은 번호로 다시 보냅니다.
  5. 로그는 한 줄씩, 통신 태스크가 찍습니다. 설비 태스크의 로그도 큐를 거쳐 나갑니다.

설비 태스크의 상태

상태뜻다음으로 넘어가는 때
BOOT막 켜짐. 안전 자세를 잡고 "켜졌다"를 신고신고를 넣으면 바로 IDLE
IDLE차체를 기다림. 리더기를 50ms마다 읽음태그를 읽으면 "태그 읽음"을 신고하고 WAIT
WAIT작업 허가를 기다림엣지 서버가 "작업 중(WORK)"을 보내면 WORK
WORK작업 동작을 함동작이 끝나면 "작업 끝"을 신고하고 DONE
DONE"작업 끝"에 대한 답을 기다림답이 오면 IDLE
FAULT비상정지나 이상. 설비를 안전 자세로 두고 멈춤원인이 없어지고 현장 버튼을 길게 누르면 IDLE

"끊김"은 상태가 아니라 덧씌우는 표시입니다. 끊겨도 하던 작업은 끝내고, 새 작업만 받지 않고, "작업 끝" 신고는 쥐고 있다가 다시 붙으면 같은 번호로 보냅니다.

RTOS를 썼다고 말할 수 있는 이유

말할 수 있습니다. 다만 "RTOS를 올렸다"는 틀린 말입니다. ESP32의 Arduino 환경에는 FreeRTOS가 원래 올라가 있기 때문입니다. 맞는 문장은 이것입니다.

"FreeRTOS의 태스크, 우선순위, 큐, 알림, 워치독으로 통신과 설비 제어를 나눠 설계했고, 그 효과를 숫자로 쟀습니다."

바탕이 되는 사실

항목내용
FreeRTOS의 종류ESP-IDF에 들어 있는 FreeRTOS는 원본 FreeRTOS(v10.5.1)를 코어 두 개용으로 고친 것입니다. Arduino 코어 3.3.0은 ESP-IDF v5.5를 씁니다.
setup()과 loop()이미 태스크 안에서 돕니다. 이름은 loopTask, 우선순위 1, 스택 8192바이트, 코어 1입니다.
틱1틱 = 1ms입니다. 10ms 박자는 10틱입니다.
Wi-Fi 쪽 태스크Wi-Fi 드라이버는 우선순위 23, lwIP(TCP/IP)는 18이고 둘 다 코어 0에서 돕니다.
순서를 정하는 방식코어마다 따로, 그 코어에서 돌 수 있는 태스크 중 우선순위가 가장 높은 것이 돕니다. 코어에 고정한 태스크는 다른 코어가 비어도 옮겨 가지 않습니다.
vTaskDelayUntil"지난번 깨어난 시각 + 주기"에 깨워서 오차가 쌓이지 않습니다. 보장하는 것은 깨어날 시각까지이고, 실제로 도는 시각은 인터럽트 등에 밀릴 수 있습니다.
인터럽트에서 보내는 알림알림을 기다리며 자던 태스크를 바로 깨웁니다. 인터럽트를 나가기 전에 양보를 요청해야 하고, 빼면 최대 1ms 더 늦습니다.
내장 플래시에 쓰는 동안모든 태스크가 잠깐 멈춥니다.

RTOS 기능을 어디에 쓰는가

기능우리 설계에서 쓰는 곳없으면
태스크설비 태스크, 통신 태스크MQTT 접속을 기다리는 동안 버튼, 리더기, 상태 흐름이 멈춤
코어 고정설비 = 코어 1, 통신 = 코어 0설비 태스크가 Wi-Fi 쪽 태스크와 같은 코어에서 밀려 박자가 흔들림
우선순위와 선점설비(3) > 통신(2)둘이 같은 코어에 있게 될 때 통신의 계산이 설비 박자를 밂
절대 주기설비 태스크의 10ms 박자delay(10)은 일한 시간만큼 주기가 늘고 오차가 쌓임
큐신고 큐, 명령 큐같이 쓰는 변수와 잠금이 필요해지고, 설비가 통신을 기다리게 될 수 있음
인터럽트 → 태스크 알림비상정지박자만큼 늦게 알거나, 인터럽트 안에서 긴 일을 하게 됨
태스크 워치독두 태스크 모두 등록한 태스크가 멈춰도 칩은 살아 있는 척함

틀리게 말하기 쉬운 두 가지

  • "통신이 막혀도 설비가 멀쩡한 것"은 우선순위가 아니라 코어를 나눈 덕입니다. 두 태스크가 다른 코어에 고정돼 있어서 우선순위를 뒤집어도 결과가 같습니다. 우선순위의 효과는 둘을 같은 코어에 올려야 보입니다(측정의 우선순위 시연).
  • 비상정지 알림은 대기 방식을 맞춰야 실제로 깨웁니다. vTaskDelayUntil로 자는 태스크는 알림이 와도 다음 박자까지 깨어나지 않습니다. 5단계에서 대기를 ulTaskNotifyTake로 바꿉니다.

한계

  • 우리가 가진 것은 "30분 동안 잰 최대값"입니다. 어떤 경우에도 넘지 않는다는 증명이 아닙니다.
  • Wi-Fi 쪽 인터럽트와 플래시 쓰기는 코어 1의 설비 태스크도 늦출 수 있습니다.
  • 칩이 통째로 리셋되면 두 태스크가 같이 멈춥니다. 나눈 것은 고장이 아니라 작업입니다. 진짜 차단은 비상정지 접점이 모터 전원을 끊는 배선이 맡습니다.
  • 잘 짠 loop 하나로도 같은 동작을 만들 수 있습니다. RTOS는 그것을 구조로 지키게 해 주는 방법입니다.

  • 버튼 2개(완료, 비상정지 대용), LED, 저항 220Ω·330Ω·10kΩ

  • ESP32와 노트북이 같이 붙을 2.4GHz Wi-Fi

  • 보드 패키지 esp32 by Espressif 3.3.x (4.x는 확인하지 않았습니다)
  • 라이브러리: PubSubClient 2.8, ArduinoJson 7.x, MFRC522 1.4.x

  • 비밀번호 파일: 스케치 폴더의 secrets.example.h를 secrets.h로 복사해 WIFI_SSID, WIFI_PASS, MQTT_HOST(브로커 PC의 IP), MQTT_PORT 1883을 채웁니다. secrets.h는 git에 올리지 않습니다.

노트북을 브로커로 쓰기 (Windows)

  1. C:\Program Files\mosquitto\mosquitto.conf 끝에 두 줄을 넣습니다: listener 1883, allow_anonymous true.
  2. 관리자 PowerShell에서 Restart-Service mosquitto.
  3. Windows 방화벽에서 1883 포트를 엽니다.

Mac에서는 brew install mosquitto 뒤 같은 두 줄을 담은 설정 파일로 mosquitto -c 파일 -v를 실행하고, python3 -m pip install paho-mqtt를 설치합니다.

PC 도구 (next_meeting/esp32_book/code/pc/mqtt_tool.py)

py -m pip install paho-mqtt
py mqtt_tool.py --host 192.168.0.10 watch               # factory/# 전부 보기
py mqtt_tool.py --host 192.168.0.10 reply               # 신고·태그에 {"re":n,"ok":1} 자동 답
py mqtt_tool.py --host 192.168.0.10 send P2 re=42 ok=1  # cmd 토픽으로 {"re":42,"ok":1}
py mqtt_tool.py --host 192.168.0.10 state P2 WORK 7     # state 토픽에 "작업 중, 작업 번호 7" (보관)

  • reply는 답만 합니다. "작업 중"은 손으로 state P2 WORK n을 쳐서 보냅니다.
  • watch 창은 하나만 띄웁니다. 두 개를 띄우면 서로 끊습니다.
  • 엣지 서버가 보내는 이상(fault)은 이 도구로 만들 수 없습니다.

신호선

  • RC522는 3.3V 전용입니다. 5V를 넣으면 망가집니다. GND도 잇고, IRQ 핀은 비워 둡니다.
  • WS2812B의 데이터 전압: LED를 5V로 켜면 규격상 데이터가 3.5V 이상이어야 하는데 ESP32는 3.3V를 냅니다. LED 한 개에 짧은 선이면 대개 동작하지만 실물로 확인합니다. 깜빡이거나 색이 틀리면 LED 전원을 3V3으로 바꿉니다.
  • 부저: 3.3V를 대어 "삐" 하고 계속 울리면 능동, "딱" 소리만 나면 수동입니다. 수동이면 코드에서 소리 주파수를 내 줘야 합니다.
  • 버튼: 네 다리 택트 스위치는 대각선 다리를 씁니다. 같은 쪽 다리를 쓰면 항상 눌린 것으로 읽힙니다.
  • 비상정지 스위치: 키트의 택트 스위치는 눌러야 닫히는 종류라 쓸 수 없습니다. 눌리면 잠기는 "평소 닫힘" 스위치를 따로 구해야 합니다. 책상 시험에서는 점퍼선을 GND에 꽂았다 빼는 것으로 대신합니다(빼면 비상정지).

주고받는 줄과 토픽

설비 태스크와 통신 태스크는 큐에 "줄"을 담아 주고받습니다. 줄의 모양은 기존 코드(modem.ino)와 데이터흐름 설명서의 규격 그대로입니다.

방향줄 → 토픽내용
올라감$T → …/tag태그 읽음
올라감$R → …/reportBOOT(번호 0), DONE, FAULT, SEEN, CLEAR
올라감$H → …/alive2초마다 살아 있다는 표시. 설비 태스크가 만듦
내려옴…/cmd → $Cre가 있으면 신고에 대한 답
내려옴…/state → $S상태, 작업 번호, 등 모양, 이상. 브로커에 보관되는 메시지
칩 안에서만$L,up=1 / 0통신 태스크가 2초마다 보내는 연결 상태. 5초 없으면 끊김으로 봄
연결 표시…/link붙으면 1, 끊기면 브로커가 대신 0을 올림(약 6초 뒤)

토픽의 앞부분은 factory/station/P2/처럼 공정 이름에서 만듭니다. USB로 줄을 직접 칠 때는 끝에 *와 검사값 두 자리를 붙이고, 칩 안의 큐에서는 뺍니다.

$T{"n":41,"k":"TAG","uid":"04A1B2C3"}        →  factory/station/P2/tag
$R{"n":42,"k":"DONE"}                        →  factory/station/P2/report
{"st":"WORK","job":7,"lamp":"Yb","fault":0}  →  $S,st=WORK,job=7,lamp=Yb,fault=0
{"re":42,"ok":1}                             →  $C,re=42,ok=1
  • 신고 번호 n: 1~255를 돌려 씁니다. 0은 BOOT에만 씁니다. 다시 보낼 때는 같은 번호입니다.
  • 다시 보내기: 답이 올 때까지 1초마다 5번, 그 뒤에는 5초마다 계속. 쥐고 있는 신고는 최대 4건.
  • 답과 허가는 다릅니다. "태그 읽음"에 대한 답은 "적었다"는 뜻입니다. 작업은 st=WORK가 올 때 시작합니다.
  • 같은 작업 번호의 "작업 중"이 다시 오면 무시합니다.

단계 0~9

한 대(P2)에서 0~8단계를 하고 9단계에서 넓힙니다. 박자와 스택을 재는 코드는 2단계부터 넣어 둡니다. 뒤 단계에서 박자가 깨지면 어느 단계에서 깨졌는지 바로 보입니다.

흔한 실수: 충전 전용 케이블, 시리얼 모니터가 포트를 쥐고 있음, 핀 0·2·12·15에 선이 달려 있음.

1단계태스크 없는 코드로 기준 숫자 얻기

발표에서 "전 ○초 → 후 ○ms"라고 말할 때의 "전"입니다. 태스크판을 만들기 전에 먼저 재 둡니다.

  1. modem/modem.ino를 그대로 올립니다(TEST_MODE 1, MEASURE 1).
  2. 브로커에 붙은 것을 확인한 뒤, 아래 세 경우를 20번씩 만듭니다.
    • 가. 브로커 PC의 Wi-Fi를 끔 (엣지 서버가 꺼진 것과 같음)
    • 나. 공유기나 핫스팟을 끔
    • 다. Stop-Service mosquitto (브로커 프로그램만 끔)
  3. 시리얼에 찍히는 # [측정] connect … ms와 10초 동안 loop 최대 간격을 적습니다.

통과: 세 경우의 최소, 평균, 최대가 표에 채워집니다.

  • 예상은 "가"에서 약 3초이고 길면 6초입니다. 기존 코드의 setSocketTimeout(3)은 접속 대기를 줄이지 않고 그 뒤의 응답 대기에만 쓰여서, 둘이 더해질 수 있습니다.
  • "다"는 거절이 바로 와서 짧게 나옵니다. "나"에서는 connect 줄이 아예 안 찍히는 것이 정상입니다.
  • 숫자가 수십 ms로 짧게 나오면 그대로 적고, 태스크판을 계속할지 팀에 다시 묻습니다. 이미 정한 약속입니다.

2단계태스크 2개, 큐 2개, 10ms 박자

rtos_step1/rtos_step1.ino를 바탕으로 새 스케치 station/station.ino를 만듭니다. 이 단계에서는 Wi-Fi 없이, 설비 태스크가 박자를 지키는지만 봅니다.

#include <Arduino.h>

struct Msg { char line[160]; };
QueueHandle_t qReport, qCmd;          // 신고 큐(설비 → 통신), 명령 큐(통신 → 설비)
TaskHandle_t  hCtrl, hComm;

void ctrlTask(void *) {
  TickType_t wake = xTaskGetTickCount();
  uint32_t tick = 0, lastUs = micros(), jitMax = 0, late = 0;
  for (;;) {
    uint32_t nowUs = micros(), dt = nowUs - lastUs; lastUs = nowUs;
    uint32_t dev = dt > 10000 ? dt - 10000 : 10000 - dt;
    if (tick > 10 && dev > jitMax) jitMax = dev;       // 박자가 10ms에서 벗어난 최대값
    tick++;

    Msg in;
    while (xQueueReceive(qCmd, &in, 0) == pdTRUE) { /* 3단계부터 */ }

    if (tick % 200 == 0) {                             // 2초마다
      Msg m;
      snprintf(m.line, sizeof m.line, "$H{\"up\":%lu,\"st\":\"IDLE\"}", (unsigned long)(millis() / 1000));
      xQueueSend(qReport, &m, 0);
      snprintf(m.line, sizeof m.line, "#[C] jit=%luus late=%lu stk=%u", (unsigned long)jitMax,
               (unsigned long)late, (unsigned)uxTaskGetStackHighWaterMark(nullptr));
      xQueueSend(qReport, &m, 0);                      // '#'으로 시작하면 로그. Serial은 통신 태스크만 쓴다
      jitMax = 0;
    }
    if (xTaskDelayUntil(&wake, pdMS_TO_TICKS(10)) == pdFALSE) late++;   // 박자를 놓치면 pdFALSE
  }
}

void commTask(void *) {
  for (;;) {
    Msg out;                                           // 큐에서 5ms까지 기다린다 = 쉬는 시간
    if (xQueueReceive(qReport, &out, pdMS_TO_TICKS(5)) == pdTRUE)
      Serial.printf("[N] %s\n", out.line);
  }
}

void setup() {
  Serial.setTxBufferSize(1024);                        // begin 전에
  Serial.begin(115200);
  qReport = xQueueCreate(8, sizeof(Msg));
  qCmd    = xQueueCreate(8, sizeof(Msg));
  configASSERT(qReport && qCmd);
  xTaskCreatePinnedToCore(commTask, "comm", 8192, nullptr, 2, &hComm, 0);
  xTaskCreatePinnedToCore(ctrlTask, "ctrl", 6144, nullptr, 3, &hCtrl, 1);   // 마지막에 만든다
}
void loop() { vTaskDelete(nullptr); }                  // loop 태스크는 쓰지 않는다
  • 인자 읽는 법: xTaskCreatePinnedToCore(함수, 이름, 스택 바이트, 인자, 우선순위, 핸들, 코어).
  • 설비 태스크를 마지막에 만드는 이유: setup()은 코어 1의 우선순위 1 태스크에서 돕니다. 우선순위 3인 설비 태스크는 만들어지는 순간 setup()을 밀어내고 돌기 시작합니다. 그 전에 큐와 통신 태스크가 준비돼 있어야 합니다.
  • xTaskDelayUntil을 쓰는 이유: vTaskDelayUntil과 같은 동작인데, 박자를 놓쳤는지 돌려줘서 셀 수 있습니다.

통과: [N] $H…가 2초마다 나옵니다. jit(박자가 벗어난 최대)가 수백 µs 이하, late(놓친 횟수)가 0, stk(남은 스택)가 1000 이상입니다. 기준값은 처음 잡은 값입니다.

흔한 실수: 설비 태스크에서 Serial.printf를 직접 부름, delay()를 씀, 큐를 만들기 전에 태스크를 만듦. stk의 단위(바이트인지)는 6144바이트 태스크를 만든 직후 값이 6000 근처인지로 한 번 확인합니다.

3단계리더기, 버튼, 상태 LED, 상태 흐름

작업 동작은 아직 "3초 기다리기"로 대신합니다. 통신 태스크도 아직 Wi-Fi 없이, USB로 친 줄을 명령 큐에 넣는 역할만 합니다.

3-가. 리더기가 박자를 깨는지 먼저 재기

MFRC522 라이브러리는 태그가 없을 때 응답을 25ms 동안 기다립니다. 50ms마다 읽으면 그때마다 설비 태스크가 25ms씩 막혀 10ms 박자가 깨집니다. rfid.ino에서 PICC_IsNewCardPresent() 앞뒤로 micros()를 재서 확인하고, 아래처럼 기다리는 시간을 5ms로 줄인 뒤 다시 잽니다.

#include <SPI.h>
#include <MFRC522.h>
static MFRC522 rfid(PIN_SS, PIN_RST);

static void readerInit() {                      // 설비 태스크 시작부에서 한 번 (안에 delay(50)이 있다)
  SPI.begin(PIN_SCK, PIN_MISO, PIN_MOSI, PIN_SS);
  rfid.PCD_Init();
  rfid.PCD_WriteRegister(MFRC522::TReloadRegH, 0x00);   // 응답 대기 25ms → 5ms
  rfid.PCD_WriteRegister(MFRC522::TReloadRegL, 0xC8);
}
static bool readUid(char *uid, size_t cap) {    // cap은 21 이상
  if (!rfid.PICC_IsNewCardPresent() || !rfid.PICC_ReadCardSerial()) return false;
  size_t k = 0;
  for (byte i = 0; i < rfid.uid.size && i < 10; i++)
    k += snprintf(uid + k, cap - k, "%02X", rfid.uid.uidByte[i]);
  rfid.PICC_HaltA();
  return true;
}

5ms로 줄여도 태그가 잘 읽히는지는 실물로 확인해야 합니다. 그래도 박자가 깨지면 리더기를 우선순위가 낮은 셋째 태스크로 빼는 길이 있지만, "태스크 두 개" 결정을 바꾸는 일이라 팀과 정합니다.

3-나. 버튼 (짧게 / 길게 2초)

enum BtnEv { EV_NONE, EV_SHORT, EV_LONG };
struct Btn { uint8_t pin; bool stable = HIGH, last = HIGH, longDone = false; uint32_t tEdge = 0, tDown = 0; };

static BtnEv pollBtn(Btn &b, uint32_t tick) {   // 10ms마다 부른다
  bool now = digitalRead(b.pin);
  if (now != b.last) { b.last = now; b.tEdge = tick; }
  if (now != b.stable && tick - b.tEdge >= 3) {             // 30ms 동안 같아야 인정 (떨림 거름)
    b.stable = now;
    if (now == LOW) { b.tDown = tick; b.longDone = false; }
    else if (!b.longDone) return EV_SHORT;
  }
  if (b.stable == LOW && !b.longDone && tick - b.tDown >= 200) { b.longDone = true; return EV_LONG; }
  return EV_NONE;
}

3-다. 상태 흐름

enum St : uint8_t { ST_BOOT, ST_IDLE, ST_WAIT, ST_WORK, ST_DONE, ST_FAULT };
static St st = ST_BOOT;
static bool linkUp = false;
static uint32_t lastLinkTick = 0, workT0 = 0;
static int job = 0, lastJob = -1;
static uint8_t doneN = 0;

// "$S,st=WORK,job=7" 같은 줄에서 값 꺼내기
static bool kv(const char *line, const char *key, char *out, size_t cap) {
  size_t kl = strlen(key);
  for (const char *p = strchr(line, ','); p; p = strchr(p, ',')) {
    p++;
    if (!strncmp(p, key, kl) && p[kl] == '=') {
      size_t n = strcspn(p + kl + 1, ",*");
      if (n >= cap) return false;
      memcpy(out, p + kl + 1, n); out[n] = 0;
      return true;
    }
  }
  return false;
}

static void onCmd(const char *l, uint32_t tick) {          // 명령 큐에서 꺼낸 줄마다
  char v[24];
  if (l[1] == 'L') { linkUp = kv(l, "up", v, sizeof v) && v[0] == '1'; lastLinkTick = tick; }
  else if (l[1] == 'C') { if (kv(l, "re", v, sizeof v)) answered((uint8_t)atoi(v)); }
  else if (l[1] == 'S' && st == ST_WAIT && linkUp
           && kv(l, "st", v, sizeof v) && !strcmp(v, "WORK")
           && kv(l, "job", v, sizeof v) && atoi(v) != lastJob) {   // 같은 작업 번호는 다시 하지 않는다
    job = atoi(v); work->begin(); workT0 = tick; st = ST_WORK;
  }
}

static void stepState(uint32_t tick) {                     // 10ms마다
  char uid[21], extra[40];
  if (tick - lastLinkTick > 500) linkUp = false;           // $L이 5초 없으면 끊김
  switch (st) {
    case ST_BOOT: report('R', "BOOT", "", true); st = ST_IDLE; break;
    case ST_IDLE:                                          // 끊김이면 새 작업을 받지 않는다
      if (linkUp && tick % 5 == 0 && readUid(uid, sizeof uid)) {   // 리더기는 50ms마다
        snprintf(extra, sizeof extra, ",\"uid\":\"%s\"", uid);
        report('T', "TAG", extra); st = ST_WAIT;
      }
      break;
    case ST_WAIT: break;                                   // onCmd가 st=WORK를 기다린다
    case ST_WORK:                                          // 끊겨도 하던 동작은 끝낸다
      if (work->step((tick - workT0) * 10)) {
        work->safe(); lastJob = job;
        doneN = report('R', "DONE", ""); st = ST_DONE;
      }
      break;
    case ST_DONE: if (!pending(doneN)) st = ST_IDLE; break;   // 답이 오면 목록에서 빠진다
    case ST_FAULT: break;                                  // 5단계
  }
}
  • report, answered, pending은 4단계에서 완성합니다. 지금은 report가 줄을 만들어 신고 큐에 한 번 넣고, pending은 $C가 올 때까지 참을 돌려주면 됩니다.
  • work는 8단계의 작업 동작 묶음입니다. 지금은 step(ms)가 3000ms가 지나면 참을 돌려주는 가짜를 씁니다.
  • 상태 LED는 $S의 lamp 값(0, Yb, G, R, Rb)을 따릅니다.

3-라. 책상 시험

통신 태스크에, 시리얼 모니터로 친 줄을 명령 큐에 넣는 코드를 잠깐 둡니다.

static void serialToCtrl() {                    // commTask 루프 안에서 부른다
  static char buf[160]; static size_t n = 0;
  while (Serial.available()) {
    char c = Serial.read();
    if (c == '\n') {
      buf[n] = 0;
      if (n > 1) { Msg m; strlcpy(m.line, buf, sizeof m.line); xQueueSend(qCmd, &m, 0); }
      n = 0;
    } else if (c != '\r' && n < sizeof buf - 1) buf[n++] = c;
  }
}
  1. $L,up=1을 칩니다. (연결된 척. 5초 안에 다음으로 가거나 다시 칩니다)
  2. 태그를 댑니다 → $T{…}가 찍힙니다.
  3. $S,st=WORK,job=1,lamp=Yb,fault=0을 칩니다 → 3초 뒤 $R{"n":…,"k":"DONE"}.
  4. $C,re=번호,ok=1을 칩니다 → IDLE로 돌아갑니다.

통과: 위 순서를 10번 되풀이합니다. 같은 job을 다시 치면 무시합니다. late는 계속 0입니다.

  • 태그는 한 번 읽히면 뗐다가 다시 대야 또 읽힙니다. 고장이 아닙니다.
  • 허가가 끝내 오지 않을 때 WAIT에서 빠져나오는 규칙은 아직 없습니다. 30초 뒤 IDLE을 제안으로 둡니다.

4단계통신 태스크, 끊김, 다시 보낼 목록

통신 태스크에 modem.ino의 Wi-Fi와 MQTT 코드를 옮깁니다. serviceWifi(), serviceMqtt(), onMqtt()는 거의 그대로 쓰고, 줄을 다른 보드로 보내던 자리만 큐 넣기로 바꿉니다.

static uint32_t dropCmd = 0;

static void toCtrl(const char *body) {                     // body 예: "C,re=42,ok=1"

}

static void handleOut(const char *line) {                  // 신고 큐에서 꺼낸 줄
  if (line[0] == '#') { Serial.printf("%s\n", line + 1); return; }   // 로그
  const char *topic = line[1] == 'T' ? BASE "tag"
                    : line[1] == 'R' ? BASE "report"
                    : line[1] == 'H' ? BASE "alive" : nullptr;
  if (!topic || !mqtt.connected()) return;                 // 못 보내면 버린다. 설비 태스크가 다시 보낸다
  mqtt.publish(topic, (const uint8_t *)line + 2, strlen(line + 2), false);
}

void commTask(void *) {
  WiFi.mode(WIFI_STA); WiFi.setSleep(false); WiFi.begin(WIFI_SSID, WIFI_PASS);
  mqtt.setServer(MQTT_HOST, MQTT_PORT); mqtt.setCallback(onMqtt);
  mqtt.setBufferSize(512); mqtt.setKeepAlive(4); mqtt.setSocketTimeout(3);

설비 태스크에는 답을 받을 때까지 신고를 쥐고 있는 목록을 둡니다.

struct Pend { bool used; uint8_t n, tries; uint32_t nextAt; Msg m; };
static Pend pend[4];
static uint8_t seqN = 0;

static uint8_t report(char type, const char *kind, const char *extra, bool boot = false) {
  uint8_t n = boot ? 0 : (seqN = seqN % 255 + 1);          // 1~255를 돈다. 0은 BOOT만
  for (Pend &p : pend) if (!p.used) {
    p.used = true; p.n = n; p.tries = 0; p.nextAt = millis();
    snprintf(p.m.line, sizeof p.m.line, "$%c{\"n\":%u,\"k\":\"%s\"%s}", type, (unsigned)n, kind, extra);
    break;
  }
  return n;
}

static void serviceResend() {                              // 매 박자 끝에
  uint32_t now = millis();
  for (Pend &p : pend) {
    if (!p.used || !linkUp || (int32_t)(now - p.nextAt) < 0) continue;   // 끊김이면 쥐고만 있는다
    if (xQueueSend(qReport, &p.m, 0) == pdTRUE) {
      p.tries++;
      p.nextAt = now + (p.tries <= 5 ? 1000 : 5000);       // 1초마다 5번, 그 뒤 5초마다
    }                                                      // 큐가 가득이면 다음 박자에 다시
  }
}
static void answered(uint8_t re) { for (Pend &p : pend) if (p.used && p.n == re) p.used = false; }
static bool pending(uint8_t n)   { for (Pend &p : pend) if (p.used && p.n == n) return true; return false; }

시험

창 세 개를 띄웁니다: watch, reply, 그리고 state를 손으로 칠 창.

  1. 태그를 대고 state P2 WORK 1을 보냅니다.
  2. 작업 중에 브로커 PC의 Wi-Fi를 끕니다.
  3. 설비가 작업을 끝내고 "작업 끝"을 쥡니다. 약 6초 뒤 watch에 link 0이 보입니다.
  4. Wi-Fi를 켭니다 → 같은 번호의 "작업 끝"이 올라오고, 답을 받아 IDLE로 갑니다.

통과: 10번 모두 "작업 끝"의 번호가 끊기기 전과 같습니다. 끊긴 동안 태그를 대도 새 작업이 시작되지 않습니다. 끊긴 동안에도 jit와 late가 변하지 않습니다.

  • 브로커에 보관된 옛 상태가 다시 붙자마자 옵니다. 시험이 끝나면 state P2 IDLE 0 --lamp 0을 보내 지웁니다. 안 그러면 켜자마자 작업이 시작될 수 있습니다.
  • 재부팅하면 lastJob이 사라져 옛 "작업 중"을 새 작업으로 볼 수 있습니다. 저장해 둘지는 팀이 정합니다.
  • 반복 시험을 손으로 하기 번거로우면, 태그에 답하고 "작업 중"을 내고 "작업 끝"에 답하는 것을 자동으로 하는 모드를 PC 도구에 더합니다.
  • 흔한 실수: 설비 태스크에서 mqtt나 WiFi를 부름, 다시 붙은 뒤 구독을 다시 하지 않음.

5단계비상정지, 워치독, 안전한 부팅

비상정지가 설비 태스크를 바로 깨우게 하기

2단계의 대기(xTaskDelayUntil)를 아래 모양으로 바꿉니다. 다음 박자까지 남은 시간 동안 "알림"을 기다리므로, 비상정지 인터럽트가 오면 박자를 기다리지 않고 바로 깨어납니다. 알림이 없으면 원래대로 10ms마다 돕니다.

#include <esp_task_wdt.h>
static volatile uint32_t estopUs = 0;          // 측정용. "같이 쓰는 변수 0개" 규칙의 유일한 예외

void IRAM_ATTR onEstop() {                     // 인터럽트: 짧게. Serial, digitalWrite 금지
  estopUs = micros();
  BaseType_t hp = pdFALSE;
  vTaskNotifyGiveFromISR(hCtrl, &hp);          // 설비 태스크를 깨운다
  if (hp) portYIELD_FROM_ISR();                // 빼면 최대 1ms 더 늦는다
}

void ctrlTask(void *) {
  readerInit();
  pinMode(PIN_ESTOP, INPUT_PULLUP);            // 평소 닫힘: 정상 LOW, 눌리거나 선이 빠지면 HIGH
  attachInterrupt(PIN_ESTOP, onEstop, RISING); // 설비 태스크 안에서 등록한다
  esp_task_wdt_add(nullptr);                   // 이 태스크를 워치독에 등록

  const TickType_t P = pdMS_TO_TICKS(10);
  TickType_t next = xTaskGetTickCount() + P;
  uint32_t tick = 0, late = 0;
  for (;;) {
    int32_t wait = (int32_t)(next - xTaskGetTickCount());
    if (wait < 0) { wait = 0; late++; }
    bool woke = ulTaskNotifyTake(pdTRUE, wait);            // 박자까지 자되, 알림이 오면 바로 깬다

    if (woke || digitalRead(PIN_ESTOP) == HIGH) {          // 알림을 놓쳐도 핀을 다시 본다
      if (st != ST_FAULT) {
        work->safe();                                      // 먼저 멈추고
        st = ST_FAULT;
        report('R', "FAULT", ",\"c\":\"E00\",\"t\":0");     // 그다음 신고
      }
      if (woke) continue;                                  // 남은 박자만큼 다시 잔다
    }
    next += P; tick++;
    esp_task_wdt_reset();                                  // "나 살아 있다"
    // 버튼 → 명령 큐 → stepState(tick) → 출력 → serviceResend()
  }
}

  • 통신 태스크도 esp_task_wdt_add(nullptr)로 등록하고 한 바퀴마다 esp_task_wdt_reset()을 부릅니다.
  • MQTT 접속이 길면 6초까지 막힐 수 있어 8초는 여유가 크지 않습니다. 1단계에서 잰 최대값을 보고 정합니다.

이상을 푸는 법과 부팅

  • 풀기: 완료 버튼을 짧게 누르면 "봤다"(SEEN), 2초 길게 누르면 "해제"(CLEAR)입니다. 해제는 비상정지 핀이 정상(LOW)일 때만 받습니다. 해제 뒤 1초는 버튼을 무시합니다.
  • 부팅: setup() 맨 앞에서 서보를 원위치로, LED와 부저를 끕니다. esp_reset_reason()을 로그로 찍고, 그다음 BOOT를 신고합니다.
  • 서보: 코어 3.x에서는 ledcAttach(PIN_SERVO, 50, 14); 뒤 ledcWrite(PIN_SERVO, us * 16384UL / 20000UL);로 씁니다. 부저 소리도 같은 기능을 쓰므로 서로 주파수가 바뀌지 않는지 확인합니다.

통과: 비상정지 10번 모두 LED와 부저가 바로 반응하고 FAULT 신고가 올라옵니다. 비상정지를 누른 채로는 해제되지 않습니다. 설비 태스크에 일부러 for(;;);를 넣으면 8초 뒤 리셋되고, 안전 자세를 잡은 뒤 BOOT가 올라옵니다.

흔한 실수: 인터럽트 안에서 Serial을 씀, IRAM_ATTR을 빠뜨림, 태스크가 만들어지기 전에 attachInterrupt를 부름. 펌웨어가 하는 것은 표시와 신고이고, 진짜 차단은 접점이 모터 전원을 끊는 배선입니다.

6단계숫자 표 채우기

새로 만드는 것은 없습니다. 2~5단계에서 넣어 둔 계측으로 측정 결과표의 칸을 채웁니다. 측정값은 설비 태스크가 10초마다 한 줄로 만들어 신고 큐에 넣고, 통신 태스크가 찍습니다.

  • 통신 태스크도 자기 스택 남은 양과 명령 큐에 못 넣은 횟수를 같은 식으로 찍습니다.

통과: 결과표의 모든 칸에 실측값이 들어갑니다.

7단계판정 시험

태스크판으로 갈지, 기존 코드로 돌아갈지를 정하는 시험입니다. 이미 정한 조건은 30분 연속 + 엣지 서버 끄기 10번 + 비상정지 10번입니다. 책상에서는 브로커 PC의 Wi-Fi 끄기로 엣지 서버 끄기를 대신합니다.

통과 (제안): 리셋 0번(BOOT가 처음 한 번만). late 0. "작업 끝" 누락 0. 같은 작업을 두 번 한 것 0. 비상정지 10번 모두 현장 버튼으로 해제.

못 넘으면 기존 코드(modem.ino 바탕)로 돌아갑니다. 이미 있는 코드라 잃는 것이 없습니다.

8단계진짜 작업 동작 끼우기

"3초 기다리기"를 P2의 실제 움직임으로 바꿉니다. 작업 동작은 네 가지 함수의 묶음으로 약속해 두면, 나머지 코드는 건드리지 않습니다.

  • 등을 끄고 1초 뒤에 "작업 끝"을 냅니다. 태그를 읽는 동안에는 모터를 돌리지 않습니다.

9단계다른 보드로 넓히기

코드 한 벌과 둘째 보드의 점검표대로 합니다. 둘째 보드는 진짜 작업 동작을 넣기 전에, 가짜 작업으로 먼저 붙여 봅니다. 이름이 겹치거나 메시지가 섞이는 문제는 두 대일 때 가장 고치기 쉽습니다.

질문답
ESP32 Arduino는 이미 FreeRTOS인데 무엇을 더했나요?커널은 그대로입니다. 더한 것은 설계입니다. loop 하나에 있던 일을 우선순위가 다른 두 태스크로 나누고 큐, 알림, 워치독으로 묶었으며, 차이를 숫자로 쟀습니다.
왜 태스크가 넷이 아니라 둘인가요?나누는 기준이 "기다려도 되는가" 하나이기 때문입니다. 태스크가 늘면 같이 쓰는 자원과 스택, 살펴볼 범위만 늘어납니다. 리더기와 핀을 설비 태스크 혼자 써야 잠금이 필요 없습니다.
왜 코어에 고정하나요?Wi-Fi 쪽 태스크가 코어 0에 있습니다. 설비 태스크를 코어 1에 두면 그것들과 CPU를 다투지 않습니다.
10ms가 보장되나요?아닙니다. 깨어날 시각은 정해지지만 실제로 도는 시각은 밀릴 수 있습니다. 저희 값은 30분 동안 관측한 최대 ○ms입니다.
큐가 가득 차면요?설비 태스크는 기다리지 않고 실패를 바로 압니다. 신고는 "다시 보낼 목록"에 남겨 같은 번호로 다시 보냅니다. 못 넣은 횟수를 세어 표에 적었습니다.
왜 잠금(뮤텍스)과 같이 쓰는 변수가 아닌가요?잠금은 설비 태스크가 통신 태스크를 기다리게 만들 수 있고, 한 번 빠뜨리면 찾기 어렵습니다. 큐는 값을 복사해 넘기므로 같이 쓰는 메모리가 없습니다.
비상정지를 왜 인터럽트 안에서 바로 끄지 않나요?인터럽트는 짧아야 하고, 상태와 출력은 설비 태스크만 만진다는 규칙 때문입니다. 알림으로 ○µs 안에 설비 태스크가 깨어나며, 실제 차단은 배선이 합니다.
워치독이 터지면요?칩이 리셋되고, 안전 자세를 잡은 뒤 "켜졌다"를 신고합니다. 워치독은 되살리는 수단이지 나누는 수단이 아닙니다.

둘째 보드 점검표

  1. 0단계 Blink로 보드와 케이블을 확인합니다.
  2. STATION_ID를 바꾸고 USE_FAKE_WORK 1로 올립니다.
  3. 부팅 줄의 이름을 확인하고, watch에서 factory/station/P1/link 1을 봅니다.
  4. RC522 버전 줄이 0x91, 0x92, 0x88 가운데 하나인지 봅니다.
  5. 가짜 작업으로 한 사이클을 돌립니다.
  6. 끊김 한 번, 비상정지 한 번을 해 봅니다.
  7. P2와 동시에 켜서, 서로의 토픽에 반응하지 않는지와 접속이 번갈아 끊기지 않는지 봅니다.
  8. jit, late, 스택 남은 양을 확인합니다.
  9. 진짜 작업으로 바꿔 20번 돌립니다.
  10. 그 공정의 핀표를 문서에 적습니다.

아직 정해야 할 것

팀이 정할 것

  • 버튼 두 개의 역할. 문서에 "완료 · 비상정지 겸 확인"과 "완료 버튼 짧게/길게"가 함께 적혀 있습니다. 이 가이드의 코드는 뒤쪽을 따랐습니다.
  • 공정별 구동기와 센서, 그에 따른 핀표.
  • 허가가 오지 않을 때 WAIT에서 빠져나오는 시간.
  • "거부" 답의 모양.
  • 엣지 서버가 보낸 이상을, 현장에서 해제한 뒤 언제 0으로 내려 줄지.
  • 마지막 작업 번호를 꺼져도 남게 저장할지.
  • "끊김"을 상태 LED로 어떻게 보여 줄지.
  • 워치독 제한 시간(1단계 실측 뒤).

실물로 확인할 것

  • 이 문서의 모든 코드가 컴파일되는지.
  • 보드의 핀 순서가 그림과 같은지, 내장 LED가 2번인지.
  • 리더기 응답 대기를 5ms로 줄여도 태그가 읽히는지.
  • WS2812B가 3.3V 데이터로 켜지는지.
  • 키트 부저가 능동인지 수동인지.
  • 남은 스택 값의 단위.
  • 워치독의 기본 제한 시간.
  • MQTT 접속이 실제로 얼마나 막히는지(1단계).
